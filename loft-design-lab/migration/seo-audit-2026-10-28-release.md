# Выпуск на loft.tj и откат: подготовка к переносу

Дата: 28 октября 2026 года. Проверен локальный код новой сборки. Рабочий домен, DNS, Vercel-проект и поисковые отчёты в этой проверке недоступны. Изменения приложения, публикация и переключение домена не выполнялись.

## Решение по выпуску

Переезд пока нельзя считать готовым к переключению домена. Содержимое и SEO можно сохранить, но текущий проект является тестовым: **запрет индексации установлен одновременно в `server.js:19` и `vercel.json:21`**. Простое подключение `loft.tj` к нынешнему проекту оставит страницы с `noindex`.

Обратная ошибка — удалить запрет из общего тестового проекта. Его адрес `codex-projects-seven.vercel.app` должен оставаться закрытым для индексации и после подготовки боевой версии.

Сам факт `VERCEL_ENV=production` не решает задачу: у отдельного тестового проекта также есть Production Deployment.

## Подготовлено и проверено офлайн

Добавлены два скрипта: `scripts/prepare-production.mjs` и `scripts/preflight-production.mjs`. Они не публикуют сайт, не переключают домен и не меняют конфигурацию исходной тестовой сборки.

```sh
npm run build
node scripts/prepare-production.mjs --profile production --origin https://www.loft.tj
node scripts/preflight-production.mjs
```

Предварительная проверка использует проектные dev-зависимости `@vercel/routing-utils` и Ajv. Для изолированной установки инструментов доступен аргумент `--routing-tools /путь/к/инструментам`; он не нужен при обычном `npm ci` со всеми dev-зависимостями.

Генератор требует явные профиль и origin, отказывает при других значениях и создаёт `release/loft-production`. В артефакт попадают только выбранные runtime-файлы, семь страниц, стили, API, публичные материалы, исходники и скрипт сборки, package/lock. `.env`, `.git`, `.vercel`, `node_modules`, тесты, отчёты и данные миграционного черновика не копируются. Генератор не затирает чужую папку или отредактированный вручную предыдущий артефакт.

В сгенерированном сервере профиль зафиксирован отдельно от `VERCEL_ENV`, индексация требует canonical host. Vercel получает условный заголовок `noindex, nofollow` для **любого host, не совпадающего с `^www\\.loft\\.tj$`**, включая статические ответы. API и технические пути дополнительно закрыты от индексации. Официальные routing-схемы и преобразование правил проверены `@vercel/routing-utils 6.6.0`; неподдерживаемая/отсутствующая проверка, неверное правило или изменённые файлы приводят к ошибке preflight.

С артефакта удалён один корневой блок `FAQPage` главной, вопросы которого отсутствуют в видимом тексте. Исходный HTML и зафиксированный манифест оригинала не меняются. Организационная разметка и разметка других страниц сохраняются.

Локальная проверка прошла на портах `127.0.0.1:3107` и `127.0.0.1:3108`, после чего оба сервера закрылись. Проверены семь canonical-страниц, тестовый/подставленный/посторонний host, дополнительный `X-Forwarded-Host`, CDN-правило для неосновных host, чистые URL и алиасы с query, реальные 404, robots/sitemap, приватные runtime-пути и повторная проверка кеша стабильных JS/CSS. Использованы только GET; переходы по Location и API-отправки не выполнялись.

`release-manifest.json` содержит SHA файлов артефакта и runtime-входов. Preflight сравнивает **все** исходные runtime-входы с подготовленным кандидатом: после правки HTML/JS/CSS/package необходимо снова выполнить подготовку. Отчёт локального запуска сохраняется в `release/loft-production-preflight.json` со статусом `LOCAL_PREFLIGHT_PASS_LIVE_GATES_PENDING` и `liveReady: false`.

Схема Vercel и локальный HTTP не доказывают реальные DNS/TLS/CDN-ответы. До переключения ещё обязательны проверки на площадке, включая HTTP→HTTPS, сгенерированный Vercel-адрес, настройки доставки заявок и согласованный откат. После финальных правок и фиксации исходного коммита кандидат должен быть пересобран заново.

## Конкретная схема производственного кандидата

1. Сохранить действующий `vercel.json` как профиль тестового адреса с обязательным `noindex, nofollow`.
2. Подготовить отдельный производственный профиль/артефакт. Он собирается из того же исходника и имеет зафиксированный commit/release ID. Выбор профиля должен быть явным, а не следовать из имени ветки или только из `VERCEL_ENV`.
3. Зафиксировать единственный основной origin `https://www.loft.tj`. Значения `VERCEL_URL`, заголовок `X-Forwarded-Host` и произвольный пользовательский `Host` не должны сами включать индексацию.
4. Для приложения включение индексации требует одновременно явного производственного профиля, правильного настроенного origin и запроса к основному домену в ожидаемом контексте выпуска. По умолчанию, при неверной конфигурации и на всех тестовых/посторонних host остаётся `noindex`.
5. Защитить **также ответы CDN и статических файлов**, а не только Express. Производственная настройка Vercel должна ставить `noindex` на сгенерированных `*.vercel.app` адресах и других неосновных host либо направлять документы/robots через общий контролируемый обработчик. Удалять общий заголовок Vercel и полагаться только на middleware Express нельзя: статический файл может обслуживаться до функции.
6. Точный синтаксис условных заголовков/маршрутизации Vercel нужно проверить по схеме конфигурации используемой версии и затем по реальным HTTP-ответам. Локальный Express-тест не доказывает поведение CDN Vercel.
7. Архивная `sculpture.html`, API, ошибки и технические страницы сохраняют запрет индексации независимо от профиля основной страницы.

Пример правила приложения, а не готовая конфигурация Vercel:

```text
configuredProduction = explicitReleaseProfile == "production-loft"
                    && configuredOrigin == "https://www.loft.tj"
                    && expectedDeploymentContext

indexable = configuredProduction
         && requestUsesCanonicalHost
         && responseIsPublicCanonicalPageWithStatus200

otherwise: noindex
```

Проверка host выполняется после нормализации: регистр, допустимый порт, недопустимые разделители/несколько значений. HTTPS проверяется отдельно на живом edge; локальный HTTP-тест моделирует host и не выдаётся за проверку TLS. Произвольный `X-Forwarded-Proto` нельзя принимать за доказательство HTTPS без известного доверенного прокси. Один `Host: www.loft.tj` в локальном запросе к тестовой сборке никогда не должен снимать `noindex`.

В HTML уже сохранены исходные `index, follow` и canonical. На тестовом адресе ограничивающий HTTP-заголовок продолжает действовать поверх них. Нынешний `robots.txt` разрешает обход страниц и позволяет поисковику прочитать `noindex`; это не нужно автоматически заменять на `Disallow: /`.

## Адреса и перенаправления

Подтверждено по коду: исходные основные адреса сохранены — `/`, `/production`, `/smm`, `/branding`, `/web`, `/booking-stars`, `/order`. Основной домен в canonical и карте сайта — `www.loft.tj`.

- Сохранить один постоянный переход с `loft.tj` на `https://www.loft.tj`, с исходными путём и query string. Текущий `server.js:25–27` делает это только при точном `Host: loft.tj`; остальные варианты и реальный HTTP→HTTPS нужно проверить на площадке.
- Обработать известные алиасы: `/index`, `/index.html`, `/production.html` и аналогичные страницы, известный завершающий `/`. Направлять на исходный чистый адрес, сохраняя query string. Сначала проверить реально использовавшиеся URL; не придумывать массовые перенаправления неизвестных адресов на главную.
- Текущий `express.static(..., { extensions: ['html'] })` в `server.js:81` позволяет отдавать HTML-файл по дополнительным адресам до явных маршрутов. Canonical полезен, но постоянные перенаправления известных дублей дают более однозначную структуру.
- GET/HEAD-перенаправления страниц могут использовать исходный 301. Если правило затрагивает POST/API, метод и тело запроса должны сохраняться либо API должен обслуживаться на нужном host без такого перехода. Нельзя получить потерю заявки из-за слепого 301 на POST.
- Неизвестный путь должен возвращать настоящий 404. Не добавлять catch-all с главной и HTTP 200 ради того, чтобы «всё открывалось».

Если основной домен и адреса не меняются, это редизайн/смена выпуска на прежнем сайте. Инструмент Change of Address в Search Console для этого не требуется.

## Кеш и обратимость

В `vercel.json:24–26` весь `/assets/` получает браузерный кеш на 30 дней; `server.js:78` задаёт такой же срок. JS собирается в стабильные имена `assets/js/loft-cinema.js` и `assets/js/loft-pages.js`. Поэтому последующие правки кода требуют обновления URL ресурсов, даже если CDN нового деплоя уже обновился.

Предпочтительно использовать имена с хешем содержимого. До такой сборки нужно либо версионировать ссылки на каждый изменяемый JS/CSS по release ID, либо задавать им короткое хранение с обязательной повторной проверкой. Для уже хешированных шрифтов длительный immutable-кеш уместен. HTML, robots и sitemap не должны получать длительный immutable-кеш.

Откат должен возвращать не только HTML, но и согласованный набор ресурсов. Старый рабочий деплой и его ассеты нельзя удалять при первом выпуске новой версии.

## Обязательные проверки кандидата

Локально, без запросов к рабочему домену:

| Случай | Ожидаемый результат |
| --- | --- |
| Обычная тестовая сборка, любой host | `noindex, nofollow` |
| Тестовая сборка + подставленный `Host: www.loft.tj` | Всё ещё `noindex` |
| Только `VERCEL_ENV=production`, без явного профиля | Всё ещё `noindex` |
| Явный профиль с неверным origin | Отказ запуска или закрытая индексация |
| Производственный профиль, тестовый host | `noindex` |
| Правильный производственный контекст и canonical origin | Страница 200, правильный canonical, без `noindex` |
| Apex/известный HTML-алиас с query | Постоянный переход на canonical URL, query сохранён |
| Неизвестный путь | 404, без подмены главной |
| Архив/API/ошибка | Неиндексируемый ответ |

Локальные проверки редиректов должны отключать автоматический переход по Location. Производственный HTTPS-контекст можно проверять чистой функцией политики или локальной HTTPS-фикстурой; нельзя выдавать подставленный недоверенный заголовок за доказанный реальный HTTPS.

После появления доступа к площадке обязательно проверить те же ответы на реальных `http/https`, apex/www и сгенерированном адресе Vercel. Это проверит DNS, сертификат, CDN и маршрутизацию, которые локальный тест не покрывает.

## Функциональный стоп-фактор: доставка заявок

Наличие рабочих настроек Telegram/AI в будущем производственном проекте не проверено. В `server.js:117–119` отсутствие `TELEGRAM_BOT_TOKEN` приводит только к записи в лог; обработчик заявки позже возвращает успешный HTTP 200. Поэтому успешный экран формы ещё не доказывает доставку заявки.

До переключения нужно проверить привязку необходимых секретов на площадке и безопасный тест обработчика с подменённым транспортом. Отправка реального сообщения в Telegram требует отдельного явного разрешения/действия пользователя; текущие проверки не должны отправлять заявки сотрудникам или клиентам.

## Порядок постепенного переключения

1. Получить подтверждённый снимок живого сайта: конечный canonical host, реальные ответы URL, текущий рабочий деплой, карта DNS, Search Console и точки получения заявок. Сейчас это внешние неизвестные.
2. Зафиксировать release ID новой сборки и старого рабочего выпуска. Сохранить текущие настройки проекта и привязок домена. Исходный репозиторий оставить неизменным.
3. Собрать и проверить производственного кандидата отдельно; тестовый сайт остаётся закрытым от индексации.
4. Если рабочий сайт действительно обслуживается Vercel, предпочтительно сохранить текущую привязку домена и возможность вернуть предыдущий production deployment. Переключение домена между проектами выбирать только после проверки фактических настроек. Наличие такого проекта сейчас не установлено.
5. Если нужны изменения DNS, менять только подтверждённые web-записи. Сохранить исходные A/AAAA/CNAME и не переносить заодно MX/TXT/SPF/DKIM/DMARC или nameserver без отдельной необходимости.
6. После проверки кандидата провести согласованное переключение, затем сразу проверить HTTPS/редиректы/индексацию/основные страницы/форму/404 на живом домене. Не совмещать первый выпуск с перестройкой URL и переписыванием всех текстов.
7. При критической ошибке вернуть предыдущий рабочий деплой или записанные web-DNS/привязки. Предыдущий сайт должен оставаться доступным для отката, а не требовать повторной сборки из памяти.
8. После выпуска наблюдать индексацию, ошибки обхода и переходы по исходным важным страницам в Search Console. Без исходных отчётов нельзя численно обещать сохранение трафика или позиций.

Этот документ фиксирует подготовленный офлайн-кандидат и условия выпуска. Он не подтверждает публикацию производственной версии, переключение домена, DNS, доставку заявок или выполненный откат.
